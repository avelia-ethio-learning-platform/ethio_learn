## Goal
Production schema changes today happen through TypeORM `synchronize` at boot, with no migrations. A routine entity edit (a column length, a rename, an enum value) can silently drop live columns or rewrite a table under an exclusive lock. Replace it with versioned TypeORM migrations that run at service boot, record a baseline on the existing production database without touching its data, and catch any entity change that ships without a migration.

Acceptance criteria:
- `synchronize` is off in every environment and cannot be turned back on by an env var. `DB_SYNC=true`, if still set somewhere, is ignored with a startup warning.
- Each of the 7 services has a baseline migration in `src/migrations/`, and runs pending migrations on boot (`migrationsRun: true`) before it starts listening.
- On a database whose tables already exist (production, any local DB built by `synchronize`), the baseline records itself as applied and changes nothing. On an empty database it creates the full schema. On a half-built schema it fails loudly.
- `pnpm -C api seed` works on an empty database without `synchronize` (CI and the README run it before the services).
- A drift check (`pnpm -C api db:check`) reports 0 pending statements per service, runs in CI after the services boot, and fails the build otherwise.
- One additive migration ships the missing indexes and drops the redundant ones from audit Appendix B (P2-14), built `CONCURRENTLY`, proving the post-baseline workflow.
- Production rollout is documented step by step, including the read-only pre-merge drift check against the production database.

## Non-goals
- Constraint or data changes that belong to later phases: the `wallet_transactions (kind, reference)` unique backstop and payment `emitted_at` (phase 3), quiz-attempt and coupon constraints (phases 3/7).
- A migration lock. Free-plan services run one instance each; see Risks.
- Moving schema creation (`docker/postgres-init.sql`) into migrations. TypeORM creates its `migrations` table inside the schema, so the schema must exist first; init.sql stays.
- Changing the ORM, the schema-per-service layout or the connection pooling.
- Running anything against production from this repo's sessions without the user's explicit go-ahead (see Rollout).

## Design and key decisions
1. **Explicit migration class arrays, not globs.** `buildTypeOrmOptions(schema, entities, migrations)`. Dev runs `ts-node src/main.ts` and prod runs `dist/`, so a glob would need `.ts` in one and `.js` in the other; importing classes works in dev, prod, the CLI and jest. Each service exports `migrations` from `src/migrations/index.ts`.
2. **`synchronize: false`, hard-coded.** No env flag can re-enable it. If `DB_SYNC` is set to true, log one warning at boot ("DB_SYNC is ignored; schema changes go through migrations"). Rejected: keeping `DB_SYNC` as a dev convenience. It is exactly the switch that leaked into production.
3. **`migrationsRun: true`, `migrationsTransactionMode: 'each'`.** Migrations run inside `DataSource.initialize()`, before Nest listens, so Render's health check waits for them. `each` gives every migration its own transaction and lets a migration opt out with `transaction = false` for `CREATE INDEX CONCURRENTLY`. Logging: TypeORM prints "Migration … has been executed successfully" only when `logging` includes `'schema'`, so when `DB_LOGGING` is off use `['schema']` (with `synchronize` off, it emits only the migration-runner lines). Not `'error'`: TypeORM's default logger prints each failing query with its parameter values, which would put emails and password hashes from a unique violation into the Render logs (plan-review S6). Migration failures still print (the `migration` log type is always on), and so do slow-query warnings.
4. **Self-guarding baseline.** A shared helper in `@ethiopialearn/common`, `baselineState(queryRunner, schema, tables)`, returns `'empty'` when none of the baseline tables exist, `'present'` when all exist, and throws (listing the missing tables) when only some exist. Each baseline's `up()` returns early on `'present'`, runs its DDL on `'empty'`. Each baseline's `down()` throws unless `ALLOW_BASELINE_REVERT=1` is set, because on production the baseline was recorded over existing tables and reverting it would drop every table in the schema. TypeORM then records the baseline in `"<schema>"."migrations"` either way. This marks production (and every local DB built by `synchronize`) as baselined on its next boot, with no hand-written INSERTs. Rejected: manually creating the 7 migrations tables and inserting rows in production (error-prone, needs a production write by hand).
5. **Generate baselines from the entities against a fresh database** (`ethiopialearn_gen` in the local container, init.sql applied so the 7 schemas exist), one `migration:generate` per service through a per-service `src/data-source.ts`. Not against a renamed schema: the generated SQL embeds the schema name. Then hand-fix the one generator bug found in research: TypeORM emits a duplicate `CREATE TYPE` when two tables in one schema share an enum (`financial.owner_type` for payments and payouts, `quality.owner_type` for qa_review_items and course_cache, `outcomes.trust_tier` for certificates and educator_tier_cache). Delete the second `CREATE TYPE` and the matching duplicate `DROP TYPE` in `down()`.
6. **Seed runs migrations instead of `synchronize`.** `seed.ts` builds its DataSource from `buildTypeOrmOptions('auth', entities, migrations)`, so schema, SSL, `migrationsRun` and the `each` transaction mode come from one place (a hand-built DataSource defaults to `all` and would throw on the auth index migration's `transaction = false`). The CI and README order (seed, then services) keeps working, and running the seed can never sync a production schema again.
7. **Drift check as a script and a CI gate.** `api/scripts/db-check.ts` (run as `pnpm -C api db:check`): for each service, build its DataSource from `buildTypeOrmOptions` and then override `migrationsRun: false`, `synchronize: false` and `installExtensions: false`. This override is what keeps it read-only: with the shared `migrationsRun: true`, `initialize()` would apply pending migrations (and create the `migrations` table) on whatever database it points at, including production during rollout step 1. Then call `driver.createSchemaBuilder().log()`, print any pending statements, exit 1 if there are any. CI runs it in the e2e job after the services boot. This is what catches an entity change merged without a migration.
8. **P2-14 indexes as the first real migration** (one per affected service), built with `CREATE INDEX CONCURRENTLY` / `DROP INDEX CONCURRENTLY` and `transaction = false`, and with matching `@Index` declarations (explicit names) on the entities so the drift check stays at 0. Scope, from audit Appendix B, only the clear wins:
   - add: `financial.payments (created_at) WHERE status='pending' AND method='chapa'` (sweep, nudges; a btree scans backwards for `ORDER BY created_at DESC`, and `@Index` can't express DESC); `financial.payments (payee_id) WHERE status='confirmed' AND payout_id IS NULL` (payout run, balance); `enrollment.video_progress (lesson_id)`; `outcomes.certificates (learner_id)`; `notification.dm_messages (thread_id, created_at)`; `financial.sponsorships (bulk_purchase_id)`.
   - drop redundant (covered by a unique or composite index): `auth.educator_profiles` `IDX_2080c94891f76ce625e19874b6` (from the `@Index({ unique: true })` on `user_id`, `api/services/auth/src/entities.ts:97`; keep `REL_2080…`, which backs the `@OneToOne` constraint); `course.courses (status)`; `enrollment.enrollments (learner_id)`; `enrollment.lesson_progress (enrollment_id)`; `enrollment.video_progress (enrollment_id)`; `quality.course_reviews (course_id)`; `notification.dm_threads (a_id)`.
   - Anything else in Appendix B (trigram search, notification composites, unique backstops) is out of scope.
   If the generator emits the index changes as plain `CREATE INDEX`, rewrite them by hand to `CONCURRENTLY`. Each new index is preceded by `DROP INDEX CONCURRENTLY IF EXISTS <name>`, so a build that failed halfway (which leaves an INVALID index with that name) is rebuilt on the retry instead of being skipped by `IF NOT EXISTS` and recorded as done. One statement per `queryRunner.query()` call: a multi-statement string runs as one implicit transaction, where CONCURRENTLY fails. `db:check` compares index names, columns and uniqueness but not partial-index predicates, so step 8 checks the `WHERE` clauses in `pg_indexes`.
9. **Developer workflow, documented in README:** change an entity → `pnpm -C api/services/<svc> migration:generate src/migrations/<Name>` against a local DB that is up to date → review the SQL (enum and rename changes need hand-written SQL; see Risks) → add the class to `src/migrations/index.ts` → `pnpm -C api db:check` is clean. Reverting: the `migration:revert` script passes `-t none`, because TypeORM wraps `down()` in a transaction in any other mode, even for a migration with `transaction = false`, and `DROP/CREATE INDEX CONCURRENTLY` can't run in one.

## Data model and migrations
- No table or column changes. New per-schema table `"<schema>"."migrations"` (created by TypeORM).
- Baseline: full current schema per service, guarded (decision 4). `down()` drops everything it created and throws unless `ALLOW_BASELINE_REVERT=1` is set; it is for local use only.
- Index migration (decision 8): concurrent builds; on the current tiny production tables each takes milliseconds and takes no write lock. `down()` recreates the dropped indexes and drops the new ones, also concurrently.
- Rollback of the whole phase: revert the merge commit and redeploy. The old code defaults to `synchronize` on when `DB_SYNC` is unset, and syncs against entities that match the schema, so it only reverses the P2-14 index swap (drops the new indexes, recreates the redundant ones). `synchronize` never drops unknown tables, so the `migrations` tables stay and are simply unused. Data rollback point: the Neon branch from rollout step 2. Before rolling forward again, delete each schema's `IndexTuning%` row, or the re-merge would find it recorded and never rebuild the P2-14 indexes (code review S1).

## Rollout and ops
Order matters. Every step that touches production is done by the user, or by a session only after the user explicitly asks for that specific action.
1. **Before merge, drift check on a rehearsal copy of production** (changed in code review B1): `db:check` straight against production would list the 13 not-yet-applied `IndexTuning` statements, because the branch's entities already include them. So create a Neon branch of production, run every service's `migration:run` against it from the feature branch, then `db:check` against it. Expected: each baseline and `IndexTuning` executed, then 0 statements for all 7 services. If anything shows up, production has drifted from the entities; stop and add a corrective migration before merging, because the baseline guard would otherwise record a schema it doesn't match. Delete the rehearsal branch afterwards. Exact commands are in DEPLOYMENT.md.
2. **Take a Neon branch/snapshot** of the production database right before merging (Neon branches are instant and free-tier friendly). That is the rollback point for data.
3. Merge. Render deploys each service; on boot each records its baseline (no DDL) and builds the indexes concurrently. Watch each service's log for `Migration Baseline… has been executed successfully` and the index migration (printed because `logging` includes `'schema'`).
4. After deploy: run `db:check` against production again (expect 0); `SELECT * FROM "<schema>"."migrations"` shows two rows per affected schema; `SELECT indexrelid::regclass FROM pg_index WHERE NOT indisvalid` returns no rows.
5. `DB_SYNC` is gone from `render.yaml`; if it still shows in the `ethiopialearn-shared` env group or a service's environment (a Blueprint sync can leave a removed key behind), it is harmless (ignored with a warning) but should be deleted.
- Logging: TypeORM logs each executed migration at boot; the DB_SYNC warning names the env var.
- Boot time grows by one catalog query per service when nothing is pending.

## Risks and open questions
- **Concurrent boots:** TypeORM has no migration lock. On the free plan each service has one instance; during a Render deploy the old instance is already running, so two migrators rarely overlap. If two did, the loser hits duplicate DDL, rolls back its transaction and the service restarts. A lock (`pg_advisory_xact_lock`, not session locks, which break through Neon's pooler) is deferred until a service runs more than one instance.
- **Enum changes later:** TypeORM's generated enum migrations rename the type to `_old` per column, which breaks for the shared enum types (`owner_type`, `trust_tier`, `pricing_type`). Documented in the README workflow: hand-write `ALTER TYPE … ADD VALUE` instead.
- **Production drift** would be masked by the guard; step 1 of the rollout exists to catch it.
- **Follow-up for phase 7 (P1-21), not this phase:** TypeORM's always-on slow-query log also prints query parameters, so slow queries can leak personal data into logs.
- **Neon pooled URL and CONCURRENTLY:** concurrent index builds run outside a transaction, which works through PgBouncer in transaction mode as long as each statement is its own query. If a build fails halfway (connection drop, restart during boot), the INVALID index is dropped and rebuilt on the retry (decision 8), and rollout step 4 checks for invalid indexes.

### Deviations
- **`db:check` is `api/scripts/db-check.mjs`, not `.ts`.** It matches the repo's `.mjs` scripts and needs no new root dependency (ts-node and `@ethiopialearn/common` are not root deps). It reads each service's compiled `dist/`, i.e. what deploys, and the `db:check` script runs `turbo run build` first (cached when nothing changed) so it can never check a stale `dist/`. The check itself is `buildSchemaCheckOptions` + `pendingSchemaChanges` in `@ethiopialearn/common` (`src/typeorm/schema-check.ts`), so the overrides have the planned unit test.
- **Per-service `src/database.ts`** exports `SCHEMA`, `entities` and `migrations`; the app module, `src/data-source.ts`, the seed and `db:check` all import it. The entity list used to live in `app.module.ts`; a second copy would let `db:check` compare a different list than the service runs.
- **`buildTypeOrmOptions` returns `PostgresConnectionOptions`** (was `TypeOrmModuleOptions`), so one object feeds both `TypeOrmModule.forRoot` and `new DataSource()`.
- **Every statement in the `IndexTuning` migrations is idempotent,** not only the new-index builds: the redundant-index drops and all of `down()` use `IF EXISTS` too. With `transaction = false`, a failure part-way keeps the earlier statements and the whole migration runs again, so a bare `DROP INDEX` would fail on the retry and wedge the boot.
- **The CI drift step waits for each service's `/health` (ports 4101–4107) first.** The gateway's health check doesn't mean every service has finished migrating, and a service listens only after its migrations ran.
- **`migration:generate` passes `-p`** (formatted SQL), so generated migrations are reviewable.
