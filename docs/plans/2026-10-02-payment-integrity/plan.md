## Goal
Make every money path in the financial service exactly-once:
- **P0-04:** a payment's confirmation is check-then-write, and the webhook and the return-page poll usually arrive in the same second, so one payment can be confirmed twice: a wallet top-up credited twice, cashback and referral rewards paid twice, two receipts.
- **P0-05:** if publishing `PaymentConfirmed` fails after the row is saved `confirmed`, nothing retries: the learner is charged and never gets access.
- **P1-12:** the webhook verifies the wrong Chapa header, so genuine webhooks are probably rejected (it fails closed; confirmation then depends on the poll and the sweep).
- **P1-14:** overlapping or crashed payout runs can pay an educator twice.
- **P1-03:** the mock checkout path (which forges a valid webhook) is guarded only by `CHAPA_MODE`.

Acceptance criteria:
- However many times and however concurrently the webhook, reconcile, sweep, coupon/wallet settlement or bank-transfer paths confirm one payment, its side effects happen once: one status change, one `PaymentConfirmed`, one top-up credit, one cashback, one referral reward, one coupon use. Failing a payment is guarded the same way.
- Every wallet credit is idempotent by `(kind, reference)`, enforced by the database.
- A confirmed payment whose access-granting event (`PaymentConfirmed` for courses, `SponsorshipGranted` for gifts and pay requests, `BulkPurchaseActivated` for bulk orders) was not acknowledged by the broker is re-published within minutes; only once every required event is acknowledged is the payment marked done. A secondary effect (coupon use, cashback, referral reward) failing never blocks confirmation or access.
- A genuine Chapa webhook (HMAC of the payload in `x-chapa-signature`) is accepted; anything else is rejected.
- Two payout runs, or a run plus a crash, never attach one payment to two payouts or disburse one payout twice; releasing a held payout twice disburses once.
- Refund approval and finalization happen once per request.
- In production, the financial service refuses to boot in mock mode or without a real webhook secret and Chapa key, and `mockComplete` refuses regardless of mode.

## Non-goals
- A general transactional outbox, publisher confirms for every event, consumer dedupe, AMQP reconnect/heartbeat fixes, DLQs (Phase 9). This phase adds confirms only for `PaymentConfirmed`.
- Coupon reservation at checkout and per-user coupon limits (P1-13, Phase 6). Coupon `uses` still increments at confirmation, now exactly once.
- Refunds after a payout (clawback) and abandoned-checkout expiry (P2-01): behavior unchanged.
- Wiring a real Chapa transfer/payout API.
- Running crons while free-plan services sleep (Phase 11, external scheduler).

## Design and key decisions
### A. Exactly-once confirmation (P0-04)
1. **One `confirmPayment(paymentId, source, verified)` path** replaces the confirm half of `applyVerification`, `settleInstantly` and `recordBankTransfer`.
   - Before the transaction: tamper checks (live mode requires `amount != null` and `currency === 'ETB'`; mismatch → mark failed via decision 3) and any HTTP lookups the side effects need (learner name, referral lookup).
   - In one `dataSource.transaction`: `UPDATE payments SET status='confirmed', webhook_received_at=now() WHERE id=$1 AND status IN ('pending','failed')`; continue only when `affected === 1` (the source — webhook, reconcile, sweep, wallet, coupon, bank transfer — goes in the log line only; no new column). Then, with the same manager, the effects that *are* the purchase: wallet debit (wallet purchases) and top-up credit.
   - Secondary effects run in a nested `manager.transaction` (a SAVEPOINT): coupon `uses + 1`, cashback, referral reward (`UPDATE referrals SET status='rewarded' WHERE id=$1 AND status='signed_up'`, credit only when `affected === 1`). On any error, roll back to the savepoint, log it with the payment id, and still commit the confirmation. Today `safe()` gives that isolation; moving these into the transaction must not let a cashback bug block a learner's access (plan-review S1). A failed HTTP lookup before the transaction (learner name, referral) is logged and skips only the effect that needed it.
   - After commit, only for the winner: the after-commit effects of decision 5 (access-granting events) and `WalletCredited` notifications.
   - The loser returns `{ duplicate: true }`; `reconcile` re-reads the row and reports its current status.
   - **failed → confirmed is allowed**: `verify()` is authoritative, and Chapa can report success after an earlier failure signal. Rejected: refusing it (a learner who paid would be stuck).
2. **Purpose handlers become idempotent and re-runnable:** the state change is conditional (sponsorship grant `UPDATE … WHERE id=$1 AND status NOT IN ('granted','pending_claim')`, bulk activation `WHERE status <> 'active'`), but the access-granting publish (`SponsorshipGranted`, `BulkPurchaseActivated`) runs whenever the payment's effects are not yet marked done, so the cron can retry a lost publish (decision 5). A changed row is no longer the condition for publishing.
3. **Failing is guarded too:** `UPDATE payments SET status='failed' WHERE id=$1 AND status='pending'`; emit `PaymentFailed` only when `affected === 1`. A signed `failed` webhook is now also checked with `verify()` before failing the row (a success from verify confirms it instead).
4. **Idempotent wallet credits:** `growth.credit(userId, amount, kind, reference, manager?)` inserts the `wallet_transactions` row with `INSERT … ON CONFLICT DO NOTHING RETURNING id`; only if a row was inserted, it ensures the wallet row (`INSERT INTO wallets … ON CONFLICT (user_id) DO NOTHING`) and applies `UPDATE wallets SET balance_etb = balance_etb + $2 WHERE user_id=$1`. Using `ON CONFLICT DO NOTHING` (not catching 23505) keeps the surrounding transaction usable. `debit` gets the same treatment for kind `purchase`, with a balance check in the `UPDATE … WHERE balance_etb >= $2`. Backed by the partial unique index in the migrations section. `admin_adjust` stays non-unique (its reference isn't per event). The referral `claim` (`growth.service.ts:300-318`) catches the new `referrals(referred_user_id)` unique violation (23505) and returns the existing referral, keeping it idempotent instead of a 500.
### B. Refunds
5a. `decide`: `UPDATE refund_requests SET status=$new WHERE id=$1 AND status='pending'`; act only on `affected === 1`. `finalizeApproval`: `UPDATE payments SET status='refunded' WHERE id=$1 AND status='confirmed'`, emitting `RefundApproved` only on `affected === 1`. `request`: partial `UNIQUE refund_requests(payment_id) WHERE status IN ('pending','approved')`, with 23505 mapped to 400 "a refund is already open for this payment".
### C. No lost access (P0-05)
5. **`effects_completed_at` on payments, for every purpose** (plan-review S2). The access-granting event of each purpose — `PaymentConfirmed` (course), `SponsorshipGranted` (gift, pay request), `BulkPurchaseActivated` (bulk) — is published through a new `EventBusService.publishConfirmed(type, payload, { timeoutMs: 5000, correlationId })`: a lazily opened confirm channel on the existing connection, `publish` then `waitForConfirms()` raced against the timeout; the channel resets in the existing close handler. When every required publish for the payment succeeded: `UPDATE payments SET effects_completed_at=now() WHERE id=$1 AND effects_completed_at IS NULL`. Top-ups have no required event and are marked at confirmation.
   - **The required event follows the purpose row's current status** (plan-review round 2 B1): course → `PaymentConfirmed`; gift or pay request whose sponsorship is `granted` → `SponsorshipGranted`; sponsorship `pending_claim` (recipient has no account yet, the `invite()` path) → `SponsorshipInvited`, published once and then the payment is done (the later `SponsorshipGranted` at the recipient's signup is a separate flow and not this payment's concern); bulk `active` → `BulkPurchaseActivated`; nothing to publish → done immediately. So the cron never re-sends an invitation to an outside address and never publishes a grant with a null recipient. The call is wrapped so a broker failure neither skips other side effects nor fails the webhook (the webhook must answer 200 once the payment is confirmed). `correlationId = payment.id` gives Phase 9's consumer dedupe a key. Existing `publish()` is unchanged.
6. **Re-run cron `completePendingEffects`**, every 2 minutes, independent of `CHAPA_MODE` (today's sweep returns early in mock mode): `status='confirmed'`, any purpose, `effects_completed_at IS NULL`, confirmed more than 60 s ago, oldest first, 50 rows; it re-runs the payment's idempotent after-commit effects (decision 2). Refunded rows are excluded by the status filter. An in-process `running` flag skips a tick while the previous run is still going (with the broker down a run can take 50 × 5 s, longer than the interval), and a run stops at the first **broker** failure (publish timeout, connection or channel error), since a dead broker won't recover mid-batch (plan-review S4). A row that fails for a row-specific reason (missing data, a handler error) is logged and skipped, so one poisoned row can't block healing for the rest (round 2 S7).
   - Accepted risk: a confirm that times out although the broker got the message causes one duplicate receipt and stats bump (enrollment is already idempotent) until Phase 9's consumer dedupe. Far better than a paying learner without access.
### D. Webhook signature (P1-12)
7. **Authenticate with `x-chapa-signature` only.** Trim and lower-case, require 64 hex characters, `timingSafeEqual` against HMAC-SHA256(secret, raw body); also accept HMAC-SHA256(secret, `JSON.stringify(JSON.parse(raw))`), because Chapa's sample code signs re-serialized JSON and which bytes it signs in practice is unverified. Ignore `chapa-signature` for authentication: it is the same constant on every webhook, so anyone who saw one could replay it with any body. Header selection moves into the service (`handleWebhook(raw, headers)`) so it is unit-testable.
### E. Payouts (P1-14)
8. **Claim per payee in one transaction.** Page payees with a keyset cursor (`GROUP BY payee_id ORDER BY payee_id LIMIT 100`). Per payee, outside the transaction: trust tier once, candidate payment ids past the hold window (LIMIT 1000), one `refund_requests` lookup with `In(ids)`, fraud-hold count. Then in one transaction: `SELECT pg_try_advisory_xact_lock(hashtextextended('payout:' || $payee, 0))` (skip the payee when false; transaction-scoped because the Neon URL is pooled), `UPDATE payments SET payout_id=$p WHERE id = ANY($ids) AND payout_id IS NULL AND status='confirmed' RETURNING id, amount_etb`, compute gross from the returned rows only, insert the payout with `id=$p` as scheduled or held. The claim UPDATE is the real guarantee; the lock just avoids wasted work.
9. **Disburse once:** after commit, `UPDATE payouts SET status='paid' WHERE id=$1 AND status='scheduled'`, publishing only on `affected === 1`; `release` uses `WHERE status='held'`. A crash after commit leaves a `scheduled` payout that the next run disburses, so `payout.id` is the idempotency key for a future Chapa transfer.
### F. Mock path and financial production config (P1-03)
10. Financial passes its rules to `assertProductionConfig`: `CHAPA_MODE === 'live'`; `CHAPA_SECRET_KEY` present and starting `CHASECK` (warn on a test key); `CHAPA_WEBHOOK_SECRET` present, at least 16 characters and not the `.env.example` default. Remove the literal webhook-secret fallbacks (`payment.service.ts:460,628`); the `CHAPA_SECRET_KEY` placeholder stays for mock mode only. `mockComplete` throws Forbidden when `NODE_ENV === 'production'`, whatever the mode.

## Data model and migrations
Financial migrations (Phase 2 pattern; entities updated to match so `db:check` stays at 0):
- **Migration 1 (transactional):** `ALTER TABLE financial.payments ADD COLUMN effects_completed_at timestamptz NULL`; backfill `effects_completed_at = COALESCE(webhook_received_at, created_at)` for `status IN ('confirmed','refunded')`, so the new cron doesn't re-run every historical sale, **except** confirmed course payments with no matching `enrollment.enrollments (learner_id, course_id)` row: those are past P0-05 victims (paid, no access) and stay NULL so the cron heals them (`activate` is a no-op for an existing active enrollment). This one-off backfill reads the enrollment schema on purpose; it is the only cross-schema statement and runs once (plan-review S3). It is guarded with `to_regclass('enrollment.enrollments')`: on a fresh database (CI starts services in parallel, so financial may migrate before enrollment) the table doesn't exist yet, there are no historical payments either, and the backfill marks everything without the NOT EXISTS clause (round 2 S6).
- **Migration 2 (`transaction = false`, drop-if-exists first, one statement per query):**
  - `UNIQUE (kind, reference) ON financial.wallet_transactions WHERE kind IN ('topup','cashback','referral_reward','purchase')`
  - `UNIQUE (referred_user_id) ON financial.referrals WHERE referred_user_id IS NOT NULL`
  - `UNIQUE (payment_id) ON financial.refund_requests WHERE status IN ('pending','approved')`
  - `(webhook_received_at) ON financial.payments WHERE status='confirmed' AND effects_completed_at IS NULL` (the cron's scan)
- Each unique index fails on existing duplicates, so rollout step 1 checks production first. `down()` drops indexes and the column (local only).

## API contract
No new endpoints. Behavior changes:
- `POST /payments/webhook` (Chapa): 200 for a valid `x-chapa-signature` (including duplicates, which are no-ops); 401 for a missing or invalid one, including a `chapa-signature`-only request.
- `POST /payments/:id/reconcile`: unchanged shape; reports the current status, whichever path confirmed it.
- `POST /payments/mock/complete`: 403 in production.
- `POST /refunds`: 400 when a refund is already open for the payment.

- **Which bytes Chapa signs** (raw vs re-serialized) is unverified; decision 7 accepts both. If Chapa signs something else, the webhook still fails closed and the poll and sweep confirm, as today.

### Deviations
- **One savepoint per secondary effect** (coupon use, cashback, referral reward) instead of one shared savepoint: a cashback bug no longer loses the coupon count or the referral reward too.
- **Live verify without an amount or currency** is not confirmed and stays pending (`amount not verified`, the sweep retries); only an actual amount or currency mismatch fails the payment.
- **The mock gateway records the dev checkout's outcome** (`MockChapaProvider.settle`, called by `mockComplete`), so a signed mock "failed" webhook verifies as failed; with decision 3, the old always-success mock verify would have confirmed it.
- **`publishConfirmed` waits on the per-message publish callback** of the confirm channel rather than `waitForConfirms()`: the same broker ack, not delayed by other in-flight publishes. Any failure is a `BrokerPublishError`; the cron stops only on that type.
- **Payout claim:** conditional `UPDATE … SET payout_id` then `find({ payout_id })` in the same transaction, instead of `UPDATE … RETURNING`; equivalent, and testable through the repository API. The payee page is a raw `GROUP BY` query; per-payee candidates are capped at 1000 (oldest first).
- **A run disburses leftover `scheduled` payouts first** (decision 9's crash recovery). This also pays payouts that `FraudFlagResolved` moved back to `scheduled`, which nothing disbursed before. So that handler now releases only fraud holds and re-applies the KYC rule: above the threshold, a payout stays held as `kyc_required` (code review round 1, B1). Rollout step 1 lists existing scheduled payouts for review.
- **e2e-payments races webhook against webhook only:** in mock mode `reconcile` doesn't verify, so it's called once after the race and must report `confirmed`. Every path shares the one conditional UPDATE; cross-path races are unit tests (code review round 1, S1).
- **Cron scan:** besides `webhook_received_at < now-60s` it also takes confirmed rows with a NULL `webhook_received_at` (by `created_at`), so a legacy victim without a confirmation time isn't skipped forever.
- **Webhook:** a refunded payment returns early (no verify); the controller maps `invalid signature` to 401 and treats a missing body as unsigned; `PaymentFailed` and `WalletCredited` publishes are best effort (logged), so a webhook answers once the row changed.
- **Production rules** plug in through a new `rules` hook (`ProductionConfigSpec.rules`, `BootstrapOptions.productionRules`); `CHAPA_MODE` must be exactly `live` (unset counts as not live). The test-key warning is logged from `financial/src/main.ts`.
- **`isUniqueViolation` moved to `@ethiopialearn/common`**; auth's membership service imports it (two-line change) instead of keeping a copy.
- **Unit-test fake:** `financial/src/testing/fake-db.ts` (excluded from the build) models conditional updates, find operators, partial unique indexes (23505), `ON CONFLICT DO NOTHING`, savepoint rollback and advisory locks. Real-SQL behaviour is proven by `e2e-payments.mjs` on Postgres.
